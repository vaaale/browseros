Step: specify. First decide the **App Target**: `bos-core`, `builtin-app`, `marketplace-item`, or `n/a` (see the target reference table in SKILL.md). `marketplace-item` covers an app facet, a service facet, or both together — don't invent a separate "service" target; a spec that needs both a UI and a background daemon is still one `marketplace-item`. If it's genuinely unclear at specify time (e.g. built-in vs. marketplace hasn't been decided yet), default to writing it as `bos-core` under `/Specs/user-specs/<project-id>/` (below) with the App Target marked `[NEEDS CLARIFICATION]`, and resolve it no later than `clarify`. If it resolves to `marketplace-item` at that point, migrate it yourself: `file_read` the current spec.md, `app_spec_create({ name, specBody: <that content, App Target updated> })`, then `file_delete` the old `/Specs/user-specs/<project-id>/<id>/` location — there's no automatic move.

**Before deciding `bos-core` because the feature needs a protocol handler, arbitrary HTTP verbs, or a continuous background process, read `references/target-marketplace-item.md` first.** That reasoning ("Next.js can't handle X, therefore this needs BOS source") is exactly the mistake that reference exists to catch — such a need is usually a signal for a `marketplace-item`'s service facet (an installed item's own worker-thread process on its own port, entirely outside Next.js), not new `src/` routing. Don't let an Assumptions/Dependencies section bake in "must modify src/middleware.ts" (or similar) without checking this first — once written into spec.md, `plan` and `implement` will build on it as agreed fact.

**Where spec.md lives depends on the target — this is a physical split, not just a field:**
- **`marketplace-item`**: read `/Templates/spec-template.md` with `file_read` to build the body (prioritized, independently-testable user stories; functional requirements; measurable success criteria; mark unknowns with `[NEEDS CLARIFICATION]`), then call `app_spec_create({ name, specBody })` in ONE step — this brings the item itself into existence (symlinked, git-committed), spec included, even before any app/service/plugin code exists. Don't choose an NNN-slug id for this: `app_spec_create` derives the item's own id from `name` (flat namespace, matching `app_install`/`app_build`'s own id convention — see `references/target-marketplace-item.md`'s "Choosing an id"), or pass an explicit `id` yourself. Set the body's **App Target** field to `marketplace-item`.
- **`bos-core` / `builtin-app` / `n/a`**: specs live one level deeper than they used to — under a **Project**, `/Specs/<store>/<project-id>/<NNN-feature>/spec.md`, not directly under the store. `bos-system-specs` is **read-only, unconditionally** — never write there; a real customization to BOS core (including a built-in app) goes to **`user-specs`** instead. Pick an existing Project with `file_list('/Specs/user-specs')` (each top-level entry with a `project.json` is one — e.g. the default "user" project seeded from pre-existing content), or start a new one for a distinct area of work by writing `/Specs/user-specs/<new-id>/project.json` (`{"label": "...", "description": "..."}`) — creating a Project's own manifest needs no active branch. `user-specs` is writable only on a real feature branch (the SAME `bos/*` branch used for BOS-source delegation) — if `file_write` fails asking you to activate one, call `dev_branch_request` first (prompts the user for a name), then retry. Choose a feature id with the NNN-slug convention scoped to THAT Project only (`file_list('/Specs/user-specs/<project-id>')` to find its highest existing number; next = +1 — numbering resets per Project, not per store). Read `/Templates/commands/specify.md` and `/Templates/spec-template.md` with `file_read`, then write `/Specs/user-specs/<project-id>/<id>/spec.md` with `file_write` following the template — same content rules as above. Set the body's **App Target** field accordingly; don't leave it as the template placeholder.

**You write spec.md. Nothing else.** Not `service.json`, not `index.js`, not any config file, not a sketch of what the item will look like — even to make the spec feel more concrete (this applies to `app_spec_create`'s `specBody` too: it's still just spec.md content, never implementation). Implementation is a later, separate, delegated step (`implement`) — writing any implementation-shaped file during `specify` has happened for real and cost an entire session to (incompletely) undo. If you want to illustrate a shape, describe it in prose or a fenced code block INSIDE spec.md — never as its own file.
